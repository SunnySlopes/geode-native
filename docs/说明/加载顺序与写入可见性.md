# 加载顺序与写入可见性（A/B/C）

本文说明本轮为紫水晶子模块新增的三层修正，以及它们各自的边界。
**默认取值不变**：`--write-order max` 与既有输出逐位一致。

## 为什么需要这三层

原版 `GeodeFeature.place()` 里，形状与母岩选点都与加载顺序无关
（RNG 由 `setFeatureSeed(decorationSeed, globalIndexOfFeature, stepIndex)` 重置，
噪声由 `NOISE_PARAMETERS.create(new WorldgenRandom(...level.getSeed()))` 固定）。
真正随顺序变化的是"算出来的方块能不能落地"：

1. 晶洞体积是 33³（`minGenOffset..maxGenOffset` = ±16），**必然跨 1 圈邻居区块**。
2. `ChunkPyramid` 给 FEATURES 的 `blockStateWriteRadius(1)` 刚好够覆盖这一圈。
3. 但 FEATURES 对邻居只保证到 **TERRAIN**。邻居一旦先升到 FULL，
   `ChunkStatusTasks` 会用 `new ImposterProtoChunk(levelChunk, false)` 替换它；
   `ImposterProtoChunk.setBlockState()` 在 `allowWrites == false` 时直接 `return null`
   ——**写入被静默丢弃**。`WorldGenRegion.setBlock()` 只查写区半径，不查目标是否只读。

所以同一座晶洞在不同加载顺序下，母岩的"存在性"会变，而被选中的母岩集合不变。

## A：写入可见性

`src/geode.hpp` 新增：

- `enum class ChunkWrite { Terrain, Features, Sealed }`
  —— 目标区块此刻是"仅地形 / 正在装饰 / 已 FULL 写保护"。
- `Simulator::writable(ChunkWrite)` —— 只有 `Sealed` 不可写。
- `Simulator::in_write_zone(src_x, src_z, x, z)` —— 写区半径 1，棋盘距离。
- `Simulation::own_budding` / `spilled_budding` —— 把母岩拆成
  "落在源区块内（必然落地）"与"跨到邻居（取决于邻居状态）"。
- `Simulator::generate(cx, cz, terrain, split)` —— `split=true` 时填充上述两栏与
  `budding_bounds`。默认 `false`，开销与取值都不变。

## B：加载顺序模型

- `enum class WriteOrder { Parallel, Lexicographic, ReverseLexicographic, Isolated }`
- `Simulator::resolve(cx, cz, order, terrain)` —— 按模型裁定后返回确定值。
- `apply_write_order(sim, cx, cz, order)` —— 对已有的 Simulation 只做裁定，不重算几何。
- `refine_center(o, x, z)` —— **独立复核接口**，只对给定中心重算，供上层只处理榜单前 N 名。
- `Bounds { lower, upper, value }`：`lower` = 跨界写入全丢，`upper` = 全落地。

语义对照：

| write_order | 跨界写入 | 说明 |
|---|---|---|
| `max`（默认） | 全部保留 | 等于既有取值，即"最大取值" |
| `parallel` | 全部保留 | 同批次并行，双方都是 ProtoChunk，故与 `max` 相同 |
| `lexicographic` | 字典序小的邻居被丢弃 | 大者后装饰 |
| `reverse-lexicographic` | 字典序大的邻居被丢弃 | 小者后装饰 |
| `isolated` | 全部丢弃 | 单区块孤立加载 |

## C：前后特征覆写

`src/overwrites.cpp`（新文件）建模两个方向的覆写：

- **晶洞之前**：step 1 的 `lake_lava_underground`（salt 10000）、
  `lake_lava_surface`（10001）。落入湖体液面的岩浆构成 `geode_invalid_blocks`，
  会让 `GeodeFeature` 的控制点判定提前作废整座晶洞。
- **晶洞之后**：step 3 的 `monster_room`（30002）/ `monster_room_deep`（30003）。
  地牢外壳（dy=-1 与 dy=4 两层）必须全为固体才生成，否则整座放弃。

同时把控制点谓词对齐原版：

- 原先用 `!terrain->solid(...)`，把基岩当成"非固体"之外还漏掉了水/岩浆语义。
- 现在 `Terrain::geode_invalid()` 实现 `state.isAir() || state.is(geode_invalid_blocks)`：
  基岩（含 -64 整层与 -63..-59 锯齿层）、水、岩浆都算无效。

特征 salt 由 `test/feature_order.py` 从原版 biome JSON 反推（`FeatureSorter`
的按 step 拓扑序），并用已知的 `amethyst_geode = 20002` 校验通过。

## 接口与开关

```
--refine-top 10                 只复核榜单前 N 名（默认 10）
--write-order max|parallel|lexicographic|reverse-lexicographic|isolated
--no-precise-overwrites         关闭 C 的覆盖模型
```

上层接口不变：`Results.centers` 的 `budding` 仍是整数估计值。
JSON 额外回显 `refinedCount` 与 `writeOrder`，便于确认复核是否发生。

## C 的精确模型（本轮）

### 已精确实现

**岩浆湖 `lake_lava_underground` / `lake_lava_surface`**（salt 10000 / 10001）
不再用 16×8×16 包围盒，而是逐位复现 `LakeFeature` 的椭球网格：
`spots = nextInt(4)+4` 个随机椭球取并集，`yy<4` 写流体、`yy>=4` 写空气。
判定改用 `grid[(xx*16+zz)*8+yy]`，与原版索引一致。
放置高度也按原版走：`environment_scan(down,32)` → `surface_relative_threshold(OCEAN_FLOOR_WG, max=-5)`。

**地牢 `monster_room` / `monster_room_deep`**（salt 30002 / 30003）
不再用包围盒，改为 `RoomEntry{ox,oy,oz,xr,zr}` 的精确范围，
并实现原版两条前置检查：
- 外壳 `dy=-1` 与 `dy=4` 两层必须全为固体；
- `holeCount ∈ [1,5]`（外围 `dy=0` 且该格与其上方都是空气的计数）。

### 证明无法影响母岩数（因此不实现）

**`spring_*`**：`SpringFeature.place` 要求
`currentState.isAir() || currentState.is(validBlocks)`，而 `spring_water` /
`spring_lava` 的 `valid_blocks` 只含
stone/granite/diorite/andesite/deepslate/tuff/calcite/dirt/snow_block/powder_snow/packed_ice
——**不含** `budding_amethyst` 或 `amethyst_block`。故 spring 不会替换母岩。
它也只在 `yy=0` 一格写流体，不影响已落地的母岩。

**`scheduleTick` 裂缝回填**：该调用只出现在裂缝分支
（`GeodeFeature` 的 `distSumCrack >= crackSize` 分支，写的是空气），
其相邻格是裂缝内腔。`budding_amethyst` 不在 `#replaceable` 中，
流体只能流入 air/replaceable，**无法替换母岩**。
因此"裂缝流体回填"只会改变空气腔的填充，不改变母岩数。

### 因数据缺失无法精确实现

**`fossil`**（salt 30000/30001，仅 desert / swamp / mangrove_swamp 三群系）
反编译源码里的 `data/minecraft/structure/fossil/*.snbt` 模板
**方块数据已被剥离**：16 个模板的 `palette` 全部只剩 `minecraft:air`，
`data` 里每个 `pos` 的 `state` 也都是 air（对比 `igloo/top.snbt` 则保留了
`minecraft:furnace` 等真实方块）。因此无法重建化石的实际方块分布，
只能用包围盒近似——那与不实现等价，故本轮不接入。

**`mineshaft` / `stronghold`**
- 二者都在 step 3/4/5，晚于晶洞（step 2），理论上会覆写母岩。
- 但 cubiomes 快照**不含** `features/mineshaft.c`、`features/stronghold.c`
  （`third_party/cubiomes/` 下只有 biomenoise/biomes/generator/layers/noise），
  `modules.json` 里 `Structures` 模块虽登记了这两个文件，但快照未导出。
- **`stronghold` 已补上**：`src/stronghold_118/` 自带完整实现（1.18+），
  布局生成器是 `features/stronghold.c` 的 vendored 原样副本，放置逻辑
  （同心环 + 112 格生物群系重定位）也在模块内实现。只消费
  `GeodeCubiomes::Biomes`，不新增 cubiomes 模块。
  详见 `src/stronghold_118/README.md`。
- `mineshaft` 仍未接入：自行实现需移植 `MineshaftPieces.java`（1299 行）。

## 性能结论与放置决策

精确化后 C 的开销一度从 0.85 ms/中心暴涨到 **130 ms/中心**，
定位后分两步修好：

| 问题 | 修复 | 效果 |
|---|---|---|
| 地牢可行性在建表时对每个候选做 O(边长²) 地形采样，而一张表覆盖 700+ 区块 | 改为**惰性判定**：只在母岩点真落在盒内时才检查，并按盒缓存 | 130 → 2.4 ms |
| `height_world_surface` 自 y=319 逐格下扫（最多 384 次密度采样） | 改用样条近似值并缓存 | 配合上一条 |
| 逐点查询要遍历 9 个邻居区块 | 加 `has_rooms`/`has_lakes` 标志 + 区块级 `ring_cache` | 摊薄剩余开销 |

最终：**C ≈ 1.57 ms/中心，A/B ≈ 2.99 ms/中心，合计 ≈ 4.6 ms/中心**。

`--refine-top 10` 的实测总开销为 **+2.6% ~ +5.0%**（落到噪声范围内）。

**放置决策（按你的要求，以性能为依据）**：

| 项 | 位置 | 理由 |
|---|---|---|
| A/B 写入可见性 | 仅复核前 N 名 | 逐中心重算 441 区块，全量并入会让主模拟的区块数乘一个常数 |
| C 岩浆湖（精确椭球） | 仅复核前 N 名 | 逐位椭球 + 三层放置修饰器，建表代价高 |
| C 地牢（精确 + 可行性） | 仅复核前 N 名 | 依赖大量 `solid()` 采样，只能惰性求值 |
| `geode_invalid` 谓词修正 | 可考虑并入主搜索 | 纯正确性改进，成本仅 `bedrock()||...`，且已有缓存 |

## 下限的精确最小化（跨区块写入）

下限的语义是「**任意加载顺序下都必然存在**的母岩数。计算分两部分：

### 1. 源区块内的母岩（恒落地）

源区块装饰自己时目标就是自己，永远可写，这部分无条件计入。

### 2. 跨区块写入（求最小）

设 π 为「FEATURES 完成」的全序。母岩块 `b` 写在目标区块 `T`：

| 情形 | `b` 是否存在 |
|---|---|
| `T` 有晶洞且 `b` 也是 `T` 自己写的 | 必然存在（已计入第 1 部分） |
| `T` 是晶洞区块、另有写者 `C` | 存在 ⟺ ∃C: π(C) < π(T) |
| `T` 不是晶洞区块 | 最优全序可把 `T` 排到所有写者之前，必然丢失 |

因此只需在「参与跨区块写入的晶洞区块」上选一个全序，使保住的块最少 ——
这是**加权最小反馈弧集**问题，这里用**子集 DP** 精确求解：

```
dp[S] = 已排好集合 S 时，被保住的跨区块块数的最小值
把 t 排在下一位时，T 中「写者已出现」的块会保住
```

**去重关键**：同一个块可能被多个晶洞写入。存在性是「至少一个写者存在」（OR），
若按 ( 写者, 块 ) 对求和会高估。因此实现里先把每个块的写者集合压成
**位掩码**，再按掩码聚合计数。

### 回退

可见区块数超过 16 时 DP 不可行，回退到仅统计源区块母岩（仍是合法下界，但偏保守）。
对应输出字段：

| 字段 | 含义 |
|---|---|
| `buddingLower` | 最终下限（严格） |
| `buddingLowerRealistic` | 常见加载口径的下限（典型值，不是下界） |
| `buddingLowerOwn` | 下限里 own 的基数 |
| `buddingLowerExact` | `true` = 用上了 DP；`false` = 回退 |

`buddingLower - buddingLowerOwn` 即 DP 增量。回退只影响 DP 那部分，
`buddingLowerRealistic` 与 `buddingLower` 的差距（无晶洞目标区块的跨界写入）
不受 16 个区块的上限影响。

### 实测

200 个复核中心（多种子，半径 1500）：5 个中心有增量，
最大增量 6，命中时平均 +2.6。增量只来自「互相写入」的相邻晶洞对，
晶洞稀疏时收益自然很小。

### 两种口径：严格下界 vs 常见加载

上面的 DP 只能拿到「可证必然落地」的跨区块写入，增量很小。
剩下的跨区块写入分两种情形：

| 目标区块 | 能不能保证 |
|---|---|
| 有晶洞 | DP 已精确处理 |
| 没有晶洞（无已知内容） | **不能**——它仍会先装饰并升到 FULL |

关键误区：目标区块丢弃写入的原因**不是**它自己写了什么，
而是它先被包成 `ImposterProtoChunk(allowWrites=false)`。
即使一个区块一个母岩都不写，它仍然会走完流程升到 FULL。
所以「没有已知内容」推不出「写入会成功」。

不过在**同批加载**下，这些写入实际上几乎全部会落地：同批区块一起
TERRAIN → FEATURES，当 C 跑 FEATURES 时 N 还在 FEATURES，尚未封存。

因此同时输出两个值。实测（seed=1, radius=800）：

| 中心 | estimate | upper | lower（严格） | lowerRealistic（常见） |
|---|---|---|---|---|
| #1 | 1269 | 1269 | 397 | 1171 |
| #2 | 1082 | 1082 | 553 | 992 |
| #3 | 1067 | 1067 | 517 | 969 |

200 个中心上的平均差距 `realistic - lower` 约 **266**。

不变式（实测 200 个中心全部成立）：

```
own <= lower <= lowerRealistic <= upper <= estimate
```

> 注意：`lowerRealistic` 不是下界。若玩家把区块分批加载、
> 或回访已生成区域，目标区块可能先升到 FULL，
> 真实母岩数会跌向 `lower`。两个值之间就是加载方式带来的不确定性。

### 卡片展示

三个数排在**同一行**，顺序为：**上限 → 常见下限 → 下限**：

```
上限 1269 / 常见下限 1171 / 下限 397  [已核验]
```

| 界面名 | 字段 | 含义 |
|---|---|---|
| 上限 | `buddingUpper` | 带 `&&bounded` 的顺序模型确定值 |
| 常见下限 | `buddingLowerRealistic` | 常见加载口径，典型值 |
| 下限 | `buddingLower` | 任意加载顺序都成立的严格下界 |

原预估母岩数（不带 `&&bounded`）仍保留在卡片第一行，不被替代。

### 性能：要塞模型惰性化

128 次 112 格生物群系重定位是最贵的一步（约 1.0 s），布局本身只要约 46 ms。
现在拆为两步：先只枚举环几何；只有当某座要塞的近似起点落到查询区块
448 格以内时，才补做重定位 + 布局。

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 近原点（radius 1000，只复核 1 个中心） | 1220 ms | **249 ms** |
| `--refine-top 1` | 1413 ms | **463 ms** |
| `--refine-top 20` | 1466 ms | **519 ms** |

全图搜索时退化为全量计算，行为不变。

### 地图上的晶洞图标

在地图上点击晶洞图标时，面板同样给出三个口径：

```
最大母岩数 65 / 常见下限 65 / 下限 1
```

| 展示名 | 字段 | 含义 |
|---|---|---|
| 最大母岩数 | `budding` | 该晶洞的全部母岩（旧口径，不做裁剪） |
| 常见下限 | `buddingRealistic` | 同批加载下会落地的（扣除被覆写/被结构顶掉的） |
| 下限 | `buddingLower` | 任何加载顺序都必然落地的（仅源区块内） |

**口径差异**：这里只统计**该区块自己的晶洞**，
不扩展到活跃半径——因为图标代表的就是这一座晶洞；
而卡片上的三个值是以搜索中心为准的活跃区域。两者数值不同属正常。

实测（seed=1）：

| 区块 | max | realistic | lower | 说明 |
|---|---|---|---|---|
| (312,-504) | 65 | 65 | **1** | 几乎全部跨区块 → 下限极低 |
| (376,-600) | 15 | 15 | **15** | 全在自身区块 → 三者相等 |
| (392,-568) | 42 | 39 | **1** | 3 个被覆写顶掉 |
| (408,-472) | 79 | 65 | **33** | 14 个被覆写顶掉 |

### 与 `isolated` 的冲突

`isolated` 模型假设所有邻居都已封存，那不是可实现的全序：
相邻两个晶洞区块必然一先一后，先者的跨区块写入一定落地。
因此实现里把下限夹到 `upper` 以内，保证 `lower <= upper`。

## 版本可用性

精确搜索（A/B/C）对**全部受支持版本**开放：1.18 ~ 1.21.11 与 26.1 ~ 26.3。
早先只对 `generation >= 4`（1.21.9+）开放，理由是「低版本还没逐块校验过」；
该前提现已不成立，逐条证据见下表。

### 为何低版本也能精确校验

| 机制 | 版本依赖 |
|---|---|
| FEATURES 写区半径 1 + `ImposterProtoChunk` 丢弃写入 | 1.13+ 未变 |
| 岩浆湖（晶洞之前）与地牢（之后）覆写 | 未变 |
| 废弃矿井 piece 生成 | 1.19.2 / 1.20.1 / 1.21.5 / 1.21.11 的 RNG 调用序列逐条一致 |
| 矿井输出盒 | 只依赖 `min_y = -64` / `sea_level = 63`，1.18+ 未变 |
| 要塞 piece 生成 | 权重表、顺序、边界与 RNG 调用在 1.18 ~ 1.21.11 间一致 |

### 要塞的两条分界线

要塞位置不是全版本一致的，但只有两处变化：

| 分界线 | 变化 | 影响 |
|---|---|---|
| 1.18 ~ 1.19.2 → **1.19.3** | 重定位从「共用环几何随机流」改为「派生独立随机流」 | 几乎所有要塞位置变化 |
| 1.21.8 → **1.21.9** | `cherry_grove` 加入 `stronghold_biased_to` | 约 3% 的要塞位置变化 |

实测（4 个种子 × 128 座）：

```
1.20.x vs 1.21.5  =  0 座不同   ← pale_garden 是新生成的并原地已在表中，无影响
1.21.5 vs 1.21.11 = 23 座不同   ← 全部来自 cherry_grove 门控
```

把标签门控与生物群系生成分离测试：`B vs C`（同门控、不同版本生成）= **0**，
说明差异完全来自标签，而非生物群系漂移。

### generation 仍然存在

`generation` 不再决定能不能精确校验，但仍用于**紫水晶本身的形状与噪声细节**：

| 版本 | generation | 含义 |
|---|---|---|
| 1.18 / 1.18.1 | -2 | 半格距离 + 旧含水层接缝 |
| 1.18.2 | -1 | 旧形状 |
| 1.19 ~ 1.19.3 | -3 | 旧形状 |
| 1.19.4 ~ 1.20.6 | 0 | 现代形状 |
| 1.21 / 1.21.1 | 1 | 现代形状 |
| 1.21.2 ~ 1.21.8 | 2 | 现代形状 |
| 1.21.9 ~ 26.2 | 4 | 双精度噪声 |
| 26.3 | 5 | 双精度 + `float` 噪声 |

输出字段：`preciseSupported`（现在恒为 `true`）与
`preciseDisabled`（现在恒为 `false`，保留供旧客户端兼容）。

## 已核验标注

后端现在支持"已核验"标记，供页面展示：

- CLI：`results[].verified` + `results[].verification`（`order-resolved` / `estimate`）
- 桌面协议：`batch[].verified`

语义：**只有被精确顺序求解的结果**才标 `verified=true`，
即该条在 `refine_top` 覆盖范围内且 `write_order != "max"`。
`max` 只表示"最大取值"，不是真实加载顺序下的确定值，故不标核验。

上层 TS 已有渲染逻辑（`results.ts` 的 `geode.card.verified` 徽章），
无需改动前端即可显示。



复核只作用于榜单前 N 名，因此开销不随搜索区域增大而变化。
关键结论：**默认 `--refine-top 10` 的开销无法与测量噪声区分**。

测量条件：`seed=99887766, radius=6000, threads=8, scan-backend=cpu`，
取 5–7 次运行的中位数（同机同负载）。

每个候选中心的边际成本约 **3 ms**（含 A/B/C，8 线程并行）：

| 配置 | 相对纯搜索 |
|---|---|
| `--refine-top 10`（默认） | −3.5% ~ +8.2%（噪声范围内，均值约 +3%） |
| `--refine-top 50` | +9% |
| `--refine-top 100` | +18% |
| `--refine-top 200` | +29% |

分层拆解（200 个中心，各次测量绝对增量）：

| 组成 | 每中心成本 |
|---|---|
| A/B 可见性拆分 + 顺序裁定 | ≈ 2.9 ms |
| C 覆盖模型（岩浆湖 / 地牢） | ≈ 0.85 ms |

优化过程中修掉的两处浪费（都是先测出来才发现的）：

1. **重复几何计算**：原实现逐区块跑 `describe` + `generate` + `resolve`（内部再 `generate`），
   同一区块算三遍。改为一次 `generate(split=true)` + `apply_write_order`（纯裁定，不重算几何）。
2. **Terrain 缓存全冷**：原先每个中心新建一个 `Terrain`，噪声表与含水层/表面缓存全部重建。
   改为单线程共享实例（`refine_center(..., Terrain*)` 重载），批量复核则按线程各持一份。
3. **地牢可行性重复判定**：`room_feasible` 只依赖盒子与地形，却对每个母岩点重算 O(边长²) 采样。
   加盒级缓存后 C 从 1.16 → 0.85 ms/中心。

复核现已按线程并行（`parallel(top, threads)`），这是把 21 ms/中心降到 3 ms/中心的主因。

## 能否并入正常搜索

**不建议整体并入。** 理由是成本结构不同：

- 复核是**逐候选中心**重算 `(2r+1)²` 个区块，其中 `r = simulationDistance = 10`，
  即每个中心约 441 个区块。搜索阶段同样区块已在粗筛/模拟中处理。
- 若把带顺序裁定的模拟直接搬进全量扫描，相当于把主模拟循环的区块数乘以常数，
  而主模拟已占总时间约 92%（`simulateMs ≈ 1319ms / total ≈ 1447ms`）。这会让总时间线性上升。

**可以并入的部分**：C 里的 `geode_invalid` 谓词修正（基岩/水/岩浆对齐原版）
本就应该在搜索阶段生效——它是纯正确性改进，成本只是把 `solid()` 换成
`bedrock() || overwritten_before() || !solid()`，且 `overwritten_before` 有区块级缓存。
若要全量启用，建议先小范围实测再决定。

## 界面：精确计算开关（UI）

界面新增一个勾选项 + 填写框：

```
☐ 精确计算结果数（前 [ 20 ] 名）
```

- **默认不勾选**；未勾选时输入框禁用，行为与以前完全一致（`verifyTop=0`）。
- 勾选后对**榜单前 N 名**逐块重算，N 取填写值（1..500，默认 20）。
- **不改变原排名**：榜单顺序与未勾选时逐条一致。

### 卡片上展示的数值

复核后的卡片保留**原预估母岩数**，并在一行里显示三个复核口径
（顺序：上限 → 常见下限 → 下限）：

| 字段 | 含义 | 口径 |
|---|---|---|
| 原预估（`budding`） | 未勾选时会输出的值 | 不带 `&&bounded`，最大取值 |
| 上限（`buddingUpper`） | 带 `&&bounded` 的确定值 | 裁剪不可落地的跨区块写入 + 计入岩浆湖/地牢覆盖 |
| 常见下限（`buddingLowerRealistic`） | 常见加载下的典型值 | 下限 + 把「写入无晶洞目标区块」也算成功 |
| 下限（`buddingLower`） | 任意加载顺序下都成立的下界 | 源区块内母岩 + 跨区块写入的精确最小值 |

数值大小：**原预估 >= 上限 >= 常见下限 >= 下限**。
复核过的条目带「已核验」徽章（`geode.card.verified`）。

实测（`seed=1, radius=800, writeOrder=parallel`）：

```
est=1269  upper=1269  realistic=1171  lower=397
est=1082  upper=1082  realistic=992   lower=553
est=1067  upper=1067  realistic=969   lower=517
```

第 4 条超出 N，保持未复核（三值为 -1，前端不显示区间）。

### 为何固定用 parallel

界面不暴露顺序模型选择，勾选时固定传 `parallel`：
它在「不裁剪跨区块写入」上与 `max` 一致，但会计入岩浆湖/地牢覆盖，
因此上限与原估值的差异恰好来自覆盖模型。
若用 `isolated` 会把跨区块母岩全丢，与原估值差距过大。

### 传输链路

```
geode.ts (UI)  →  addon.cpp (N-API)  →  geode_host.cpp  →  tools/geode/search.cpp
   verifyTop / writeOrder              GeodeRequest        Options.refine_top / write_order
```

返回时逐层回填 `buddingEstimate` / `buddingUpper` / `buddingLowerRealistic` / `buddingLower`。

## mineshaft / stronghold 接入评估

**结论：短期不建议接入。**

### 理论上确实会影响母岩数

二者都在晶洞（step 2 LOCAL_MODIFICATIONS）之后：

| 结构 | step | 对母岩的影响 |
|---|---|---|
| `mineshaft` | UNDERGROUND_STRUCTURES (3) | 走廊/房间覆盖母岩 |
| `stronghold` | SURFACE_STRUCTURES (4) | 城墙/房间覆盖母岩 |

### 但工作量与风险都很高

**1. cubiomes 快照缺失源码**
`third_party/cubiomes/` 只有
`biomenoise.c / biomes.c / generator.c / layers.c / noise.c`。
`modules.json` 虽登记了 `features/mineshaft.c` 与 `features/stronghold.c`，
但快照**未导出** `features/` 目录。
要用就得升级 cubiomes 快照（会牵动其他引擎）。

**2. 原版实现体量**

| 文件 | 行数 |
|---|---|
| `MineshaftPieces.java` | 1299 |
| `StrongholdPieces.java` | 1771 |
| `StrongholdStructure.java` | 51 |
| 加 `ChunkGeneratorStructureState` 的同心环放置 | 224 |

尤其 `StrongholdPieces` 的房间连接图与下降梯循环，
与 `MineshaftPieces` 的支持柱/木栏杆/双层支撑逻辑，
都强依赖逐步 RNG 消耗与世界读写交错，很难只做几何近似。

**3. 当前覆盖模型的属性不匹配**
现有 `Overwrites` 是「先算放置盒 → 惰性判可行性」的轻量结构，
而 mineshaft/stronghold 的形状本身就需要完整的 piece 生成器。

### 建议路径（若今后要做）

| 阶段 | 工作量 | 风险 |
|---|---|---|
| 升级 cubiomes 快照并启用 `Structures` 模块 | 中 | 中（可能影响其他引擎） |
| 接入 mineshaft（cubiomes 提供位置，自行补 piece 覆盖） | 中偏高 | 中 |
| 接入 stronghold（同心环 + 房间图） | 高 | 高 |
| 验证 | 高 | 需要真实存档逐方块对照 |

建议先做 **mineshaft**（只需覆盖平方走廊），
并在 `--refine-top` 路径下提供单独开关，默认关闭。
